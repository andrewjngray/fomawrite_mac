# Cycle 145 — Harper, the writing engine

Decision (Andrew, 10 October 2026): Grammarly is a failed experiment; Harper (Automattic, Apache-2.0, offline) becomes the grammar and style engine, with the macOS checker as the fallback, Australian English as the default dialect with British and American as options, and a way to pull new Harper releases down periodically with a menu trigger. Plan: [docs/harper-plan.md](../../docs/harper-plan.md).

## Spike: Harper runs inside the editor page (done, this record's first commit)

- **Pinned release.** `harper.lock.json` names harper.js 2.10.0 and its npm sha512. `bin/fetch-harper` downloads the tarball, verifies the hash, and places the four files the page loads (`index.js`, `binary.js`, `BinaryModule.js`, `harper_wasm_bg.wasm`, 16 MB) in `src/editor/dist/harper/` (git-ignored). `bin/build` and CI run it; `bin/package-mac` copies Harper's licence into the bundle.
- **Serving.** The page is on `qrc:`, and Chromium's `fetch()` refuses `qrc:`, which the WebAssembly loader needs. A `fomawrite:` scheme (`src/harperscheme.cpp`; secure, CORS, fetch-capable; registered before WebEngine starts) serves `fomawrite://harper/<file>` from a downloaded update in the app's data folder when one exists, else from the bundled resources. The handler is installed from the Live pane as its view is created: installing it at startup, before any window, left WebEngine windows painting blank in the offscreen capture tests.
- **Loader.** `src/editor/src/harper.ts`: `harperLint(text, dialect)` imports the engine on demand (`LocalLinter`, on the page's thread), and returns `{start, end, kind, message, suggestions}` in UTF-16 offsets (checked with emoji: Harper's spans are JavaScript string indices). The page's content policy allows `wasm-unsafe-eval` and the scheme.
- **Measured in the app (test `harperLintsInsideTheEditorPage`):** engine ready about 2 s after the first request; a warm lint round trip under 110 ms including the test's polling; all six planted errors found (`is is`, `recieve`, `tomorow`, `their going too`, `could of`, `we was`) and Australian spellings left alone. In Node: setup 364 ms, 200 characters in 39 ms, 8,100 characters in 31 ms, 885 rules, dialects American, British, Australian, Canadian, Indian.
- **Lint kinds** (from the package's types): Agreement, BoundaryError, Capitalization, Eggcorn, Enhancement, Formatting, Grammar, Malapropism, Miscellaneous, Nonstandard, Punctuation, Readability, Redundancy, Regionalism, Repetition, Spelling, Style, Typo, Usage, WordChoice, WordOrder.

### Page (builder)

The page is the host's lint service for Harper and learns a third mark category. Contract in `src/editor/README.md` ("Harper", the bridge lists, "Spelling"); code in `src/editor/src/harper.ts`, `bridge.ts`, `spelling.ts`, `editor.css`.

- **Signals in.** `harperLoad(dialect)` (American / British / Australian / Canadian; reloading with another dialect replaces the linter), `harperLint(token, text)`, `harperImportWords(wordsJson)` (the last list is kept and imported again after every reload, and before the next lint).
- **Slots out.** `harperReady(version)` (version read from `fomawrite://harper/VERSION`, else `"unknown"`), `harperReply(token, lintsJson)` (`[{start, end, kind, message, suggestions}]`, UTF-16 offsets into `text`), `harperFailed(token, error)` (token -1: the load failed; every queued token is then failed too).
- **Rules.** Requests before the engine is ready are queued and answered in order; a reload keeps the queue; empty text answers `"[]"` at once; each token is answered once (a repeat of one still queued or in flight is ignored); a lint that throws fails only its token; lints after a failed load fail at once until the next `harperLoad` retries; a lint before any `harperLoad` starts the Australian load itself.
- **Style.** `spellingReply` ranges may carry `category: "Style"`: `.fw-style` (grey dotted, `#8a8f98`), the Grammar menu titled "Style" with "Ignore Style Suggestion", the same caret rule, and the same per-document ignore list and host slot `ignoreGrammar(text, message)` as Grammar (no new slot). Precedence where marks overlap: Spelling over Grammar over Style (stylesheet rules and `grammarAt`).
- **Dev server.** The mock host answers `harperLoad` with `harperReady("mock")` after 10 ms and `harperLint` with fixed findings ("recieve" Spelling, a doubled word Repetition, "very unique" Enhancement), so nothing loads WebAssembly there.
- **EditorBridge.** Pass-through slots `harperReady`, `harperReply`, `harperFailed`, host-side signals `harperLoad`, `harperLint`, `harperImportWords`, and signals for the app `harperReadied(version)`, `harperReplied(token, lintsJson)`, `harperLintFailed(token, error)`. `editor/dist/harper/VERSION` is now in `resources.qrc` so the page can read it.
- **Tests.** Node: `test/harper.test.mjs` (queue, ready, reply, failure, token, words, mock backend, and one real-engine test guarded by `dist/harper/harper_wasm_bg.wasm` that lints with an emoji before the word), `test/style.test.mjs` (reply parsing, classes, overlap, menu, ignore, caret rule, real-cascade CSS). Qt: `harperBridgeAnswersLintRequestsFromTheHost` (load -> ready with the served version, lint token 7 findings, empty text at once, `British` reload with an immediate lint, taught words).

### Host

The host half: Harper becomes the engine behind Source, the Live page's own underlines and the Review pane, with the macOS checker as the fallback. The page half (the bridge slots, the worker, `.fw-style`) is the other builder's; this section is what the host does and what it assumes of the page.

| Piece | Behaviour |
| --- | --- |
| Contract ([src/editorbridge.h](../../src/editorbridge.h)) | Plain pass-throughs, like `ignoreWord`/`wordIgnored`. To the page (signals): `harperLoad(dialect)`, `harperLint(token, text)`, `harperImportWords(wordsJson)`. From the page (slots): `harperReady(version)`, `harperReply(token, lintsJson)`, `harperFailed(token, error)`; the host-side signals are `harperReadied`, `harperReplied`, `harperLintFailed`. `lintsJson` is `[{start, end, kind, message, suggestions}]`, UTF-16 offsets into the text sent. |
| `HarperEngine` ([src/harperengine.h](../../src/harperengine.h)) | Owns the wiring to the bridge. `issues(text)` returns the cached answer for exactly that text, or `nullopt` after queueing one request. Requests are deduplicated by text (however many blocks hold the same prose); at most 64 texts wait (newest first), at most 16 are with the page; texts beyond 64 wait in an overflow list (4,096) and move up as the queue drains, so a large document is answered completely without flooding the page. The cache holds 4,096 answers and is dropped on a dialect or words change (a late reply to a dropped question finds no token and is ignored). A new page (`readyChanged` on the bridge) makes the engine not ready, re-queues what was in flight and sends `harperLoad` again. `harperFailed` drops the entry and emits `failed`; the text is asked for again the next time a surface wants it. `importWords` sends the **whole** learned list (not a delta) and the engine re-sends it after every `harperReadied`. |
| Kinds | Spelling is Spelling. Agreement, BoundaryError, Capitalization, Eggcorn, Grammar, Malapropism, Nonstandard, Punctuation, Repetition, Typo, Usage, WordOrder are Grammar. Enhancement, Formatting, Miscellaneous, Readability, Redundancy, Regionalism, Style, **WordChoice** and any kind a later Harper adds are Style. **WordChoice deviates from the brief's list** (which put it under Grammar): Harper reports "very unique" as `WordChoice` (checked against the pinned 2.10.0 in Node and in the app), the brief's acceptance example wants that grey, and docs/harper-plan.md names word choice as Style. One line in `HarperEngine::categoryForKind` and one in the engine test flips it. `SpellCheck::Issue::kind` keeps Harper's own name; the macOS checker leaves it empty. |
| `SpellCheck` | `setHarper`, `engine` (`writing/engine`, harper or macos, default harper), `dialect` (`writing/dialect`, Australian default; American, British, Australian, Canadian), `styleEnabled` (`writing/checkStyleWhileTyping`, default off), `harperReady`, `harperVersion`, `effectiveEngine` (harper only when the setting says harper **and** the engine is ready, else macos), `issuesIfKnown(text)` (nullopt while pending), `issues(text)` (empty while pending). Harper's answers are filtered here, not in the engine: the master switch, grammar off, the one ignore list (a word, or text and message), so ignoring needs no new lint. Style findings are always returned; surfaces decide whether to underline. `learnWord` also appends to `writing/learnedWords` (deduplicated) and imports the list into Harper; the stored list is imported when the engine attaches and after every ready. `suggestions(word)` prefers Harper's replacements seen for that word. `misspellings(text)` is unchanged (the macOS path). |
| Source layer ([src/markdownhighlighter.cpp](../../src/markdownhighlighter.cpp)) | The spelling layer asks `issuesIfKnown` for a block's prose. **Pending answers keep the old marks**: the block's last answered findings live on the block itself (`QTextBlockUserData`: prose and findings, so they follow the block when lines are added above), and while a new answer is on its way they are carried onto the new prose by a prefix/suffix diff: marks wholly inside the unchanged head or tail stay (the tail ones shifted), marks touching the edit are dropped, and a mark the edit merely extended (typing after a word) is dropped too. Typing therefore never flashes marks off and on; a block that never had marks draws none until its answer arrives. **A reply restyles directly**: `harperAnswered(text)` (connected to `SpellCheck::resultsReady`) looks up the blocks waiting on that prose (`m_pendingProse`, block numbers verified against the text, with a document scan only when a number went stale), strips the old marks from the block's layout formats by their properties, composes the new ones onto what remains, sets the formats, `markContentsDirty`, `updateBlock`. `rehighlightBlock` is never used from a reply or caret path: the document revision does not move (asserted). Settings that change the picture (engine, dialect, style on/off, words) still use `refreshSpelling` (a rehighlight, user actions). The marks: Spelling red, Grammar blue as before; **Style** a single grey underline `#8a8f98` with a wash (`#ebedf0` light, `#2e3238` dark), `SpellCategoryProperty` 3, drawn only while `styleEnabled`; where findings overlap the characters belong to spelling, then grammar, then style. `issuesInBlock` returns all three (the pane lists Style regardless of the underline setting). A mark over underlined text (a link) now remembers the underline and gives it back when the mark goes (`SpellBaseUnderlineProperty`). |
| Live page's underlines ([src/backend.cpp](../../src/backend.cpp)) | `spellingRequested` computes per segment; when any segment's answer is pending the request is stored with the outstanding texts and answered **once**, when every one has arrived (`resultsReady`), or after 2 s with what is known (a text that lands later makes the host ask the page to check again). Entries: `{from, to, category}` plus `kind` for every Harper finding; Grammar and Style entries also carry `message` and `suggestions`, Spelling entries carry `suggestions` when Harper has them. **Style entries are sent only while "Check Style While Typing" is on** (the page underlines whatever it is sent, and the contract has no style flag), and `setSpellCheck` is pushed on engine, dialect and style changes so the page asks again. |
| Review pane | `rebuildReviewIssues` also runs, debounced (the existing 300 ms timer), on `resultsReady`, and on engine, dialect and style changes. `issueMap` gains `kind`. [ReviewPane.qml](../../src/ReviewPane.qml): a **Style** filter (the filters wrap rather than overflow at 240 px), counts "1 spelling · 1 grammar · 1 style", rows tagged with Harper's kind for Grammar and Style ("Repetition", "Word Choice"), a status line under the counts ("Harper 2.10.0", "macOS checker", or "macOS checker (Harper is loading)"), and the popup shows the dialect list while Harper answers and the macOS language list otherwise. |
| Edit → Writing Checker | A submenu in [NativeMenuBar.qml](../../src/NativeMenuBar.qml): Engine (Harper, macOS), Dialect (Australian, British, American, Canadian), then Check Spelling / Grammar / Style While Typing (the two existing items moved in, ids kept). Commands in [WorkspaceCommands.qml](../../src/WorkspaceCommands.qml): `engineHarper`, `engineMacos`, `dialectAustralian`, `dialectBritish`, `dialectAmerican`, `dialectCanadian`, `checkStyleWhileTyping`. Dialects and Style are Harper's, so they dim under the macOS engine. |
| The page at startup | The Live pane's `Loader` is made active a second after the window shows (a `Timer`, `liveWarmTimer`), hidden, exactly as the existing created-on-first-use page. The engine sends `harperLoad` as soon as the bridge is ready. `FOMAWRITE_NO_LIVE_PREWARM=1` (`Backend::prewarmsLive`) turns it off; the test suite sets it in `initTestCase` so no test grows a Chromium page mid-run, and the tests that want the warm-up clear it. |

#### Startup numbers

Measured with the test `livePageWarmUpDoesNotDelayFirstPaintAndIsMeasured` (offscreen platform, so first paint is the first `frameSwapped`, not a GPU paint; three runs each, `FOMAWRITE_TEST_PREWARM=0` for "off"):

| | Warm-up off | Warm-up on |
| --- | --- | --- |
| Window created → first paint | 380–405 ms (16 ms after the window shows) | 394–401 ms (16 ms after) |
| Worst event-loop stall, 4 s after show | 9–14 ms | 10–14 ms |
| Resident, process tree (app plus WebEngine processes) | 422 MB | 901–911 MB |

Cold start to first paint does not move (the timer starts after the window shows, and creating the view stalls the loop no longer than the idle loop does), so the Loader is **not** deferred to the first keystroke. **Memory is the cost**: +480 MB. Of that the Live page's renderer is 455 MB with Harper loaded (131 MB with the page alone: measured by not answering `harperLoad`), and the app process grows 24 MB. Harper's own share is about 320 MB in that renderer. If that is too much, the lever is the page's (load Harper on the first lint request, or drop the engine after idle), not the host's. Harper is ready about 2.8–3.3 s after the window is created with Live never opened (test `harperDrivesSourceTheLivePageAndThePaneInTheRealPage`, with a stand-in page, see Limits).

#### Limits and assumptions about the page

- Built and tested without the page builder's bundle. The real-engine test ran against a scratch page half (about 12 lines in `main.ts` connecting `harperLoad`/`harperLint`/`harperImportWords` to `src/editor/src/harper.ts`, not committed), where it passed; with the committed bundle it skips. It must be run after the merge, along with the whole suite: once the real page answers, every test that opens Live gets Harper unless it chooses macOS.
- Assumed of the page: `harperImportWords` carries the **whole** list and **replaces** the dictionary; the page sends `harperReady` after every `harperLoad` (a dialect change reloads the linter) and serialises lints after the load; `spellingReply` entries with category `Style` are drawn as `.fw-style` (grey wavy), and the page ignores fields it does not know (`kind`, and `suggestions` on Spelling).
- Style findings have no right-click menu in Source (only Spelling and Grammar have); they are in the pane, with Ignore and the suggestions.
- Harper's lint config (rules on and off) is not touched; Cycle 146.
- Not installed or hand-tested in the app.

## Review and fixes (build 145)

A separate reviewer ran the merged cycle end to end in the real page: Harper ready 2.97 s after the window, all planted errors found, 319 page tests and the full Qt suite green after the fixes. Verdict: ship with fixes. Taken:

| Finding | Fix |
| --- | --- |
| `engineChanged` fired whenever Harper's readiness flipped even with the macOS engine selected, forcing a rebuild between the page's edit and its caret update (the pane listed a half-typed word; a full re-highlight and page re-check for nothing). | Emitted only when the effective engine moves. |
| A Chromium renderer death left Source with no marks for the rest of the session: the hidden page serves Source now and nothing reloaded it. | The Live pane reloads on `renderProcessTerminated`; the bridge's `ready()` re-sends `harperLoad`. Confirmed by killing the renderer in a probe. |
| Source and the pane sent Harper text the Live page did not: heading markers were linted ("use title case"), blanked link/code spans produced "two spaces" Formatting rows, hard-wrapped continuation lines produced Capitalization findings. | Whitespace-only findings dropped; heading markers blanked like the page's; Capitalization findings at the start of a continuation line dropped. All three surfaces now agree on the probe document. |
| harper.js `importWords` appends, so an unlearned word stayed accepted; the host also sent nothing for an emptied list. | The page clears before importing; the host sends an empty list once something was sent. |
| `harperFailed(-1)` (engine failed to load) was ignored: the pane said "Harper is loading" forever. | The engine drops to not-ready with the error kept; the pane says "Harper failed to load". |

Still open from the review: marks vanish once for a moment when Harper becomes ready (macOS marks go, Harper's arrive); a block split by Enter waits for its answer; list items and quotes are linted twice per edit (the page blanks `-`/`>`, the highlighter does not); the Writing Checker submenu's three toggles have no `resync()` on open; memory: about 450 MB for the page with Harper loaded, and each window has its own (896 MB resident for one window, 1.6 GB for two) — the levers are not warming the page when the engine setting is macOS, one engine shared across windows, or unloading after idle.
