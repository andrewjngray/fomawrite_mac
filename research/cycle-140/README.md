## Appearance follows the Output Style

`Backend::appearanceFollowsOutputStyle` (QSettings `appearance/followOutputStyle`, default on; View → Appearance Follows Output Style). When the selected theme defines `--bg-color`, `loadOmarchyTheme` takes it as the window background, `--text-color` (alpha dropped) as the foreground, `--primary-color` as the accent, and the background's luminance decides dark mode; themes without a page colour, basic presets, or the setting off, leave the Theme preset in charge. Re-derived on every `publishingCssChanged`. Test `appearanceFollowsTheOutputStylesPageColours` with the Lapis Dark fixture (`#1e222a` page, `#e4e4e4` text, back to Studio's `#F6F3EE` on a basic preset or with the setting off).

## Limits

- `.highlight` (`==text==`) keeps its fixed pale-yellow background and the theme's text colour: pale text on pale yellow in a dark theme. Typora's `mark` rule is theme-specific and Fomawrite emits a span.
- Live: `--md-char-color` is not applied to revealed Markdown marks; theme colours do not reach the real table widget or Live code-token colours.
- `::selection` falls back to the system `Highlight` colour (close to, not bit-identical with, the browser default) in published HTML for themes without `--select-text-bg-color`.
- Print: Lapis's `@media print` text override loses to Lapis Dark's later `:root`, so a PDF of Lapis Dark should be light text on a dark ground (not checked with the real Lapis Dark; the PDF test uses a variables-only theme).
- The variable parser does not model `!important` or selector specificity between `:root` rules.

## Build 141 — highlighted text readable under any theme (9 Oct, page/Qt agent)

The reviewer's open item. Finding on the way: Live never rendered `==text==` at all (no Highlight node in the page parser); the unreadable case was Web/PDF, where `.highlight { background: #fff2a8 }` had no text colour under a dark theme's light text. Now: the Typora base shim paints `mark, .highlight` with the theme's `--highlight-color` (fallback `--fw-highlight-bg` `#fff2a8`) and a host-computed `--fw-highlight-fg` (`TyporaBase::highlightText`: `#1a1a1a` if it reaches 4.5:1 on the highlight composited over `--bg-color`, else `#ffffff`), emitted after the shim and before the theme so a theme can still override; the Live page gained a `==highlight==` parser (exactly two `=`, GFM-style flanking, code spans excluded) rendered as `.fw-highlight` with the same pair and the `==` hidden until the caret touches; `thememap.ts` maps a theme's `mark` rule onto it. Tests: `typoraBaseChoosesReadableHighlightText`, `publishedHighlightStaysReadableOnDarkThemes` (real page, computed colour pair ≥ 4.5:1 for Lapis Dark, variables-only dark, a dark-blue highlight, a theme with its own mark pair, Lapis light, basic preset), `liveHighlightStaysReadableOnDarkThemes`; page `test/highlight.test.mjs`. **Red evidence not obtained**: the agent's worktree was removed before its red run finished (my mistake: I merged as soon as the commit appeared); the old code demonstrably had no Live highlight element and inherited `#e4e4e4` on `#fff2a8` in Web, but that was reasoned, not run. Open: a theme that sets only a dark `mark` background without `--highlight-color` can still be unreadable; published output keeps `<span class="highlight">`; Live's parser is stricter on spaces than the publisher's. Bundles: all at build 141 ([verified-builds.json](verified-builds.json)); Qt 221, page 256.
